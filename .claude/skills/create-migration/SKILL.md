# Create a migration

Alembic runs **inside the container** — the host Python cannot reach the database and is the wrong version. Every step below is a container command.

## 1. Check the models are what you want

Migrations are autogenerated from `api/app/db.py`. Edit the model first; the migration follows.

## 2. Make sure the database is current

Autogenerate diffs the models against the **live** database. If pending migrations have not been applied, the diff will be wrong — it will try to recreate things that already exist.

```bash
docker compose up -d db
docker compose run --rm api alembic upgrade head
```

## 3. Generate

```bash
docker compose run --rm api alembic revision --autogenerate -m "short description"
```

Written to `api/migrations/versions/`. The `api/` directory is bind-mounted, so it lands on the host.

## 4. Read it before applying — autogenerate is a draft

Open the generated file. Alembic reliably misses or mangles:

- **Server defaults** — `server_default=func.now()` is often dropped.
- **Index and constraint names** — check they match the model.
- **Column type changes** — frequently emitted as drop-then-add, which silently destroys data. Rewrite as `alter_column`.
- **Enum changes** in PostgreSQL — usually need hand-written `ALTER TYPE`.
- **Nullable → non-nullable** on a populated table — needs a backfill in the same migration or it fails on real data.
- **`downgrade()`** — often left as a stub. Fill it in; an unreversible migration is a trap.

## 5. Apply and verify

```bash
docker compose run --rm api alembic upgrade head
docker compose exec -T db psql -U postgres -d scamsathi -c "\d+ table_name"
```

## 6. Check it reverses

A migration that cannot roll back is not finished.

```bash
docker compose run --rm api alembic downgrade -1
docker compose run --rm api alembic upgrade head
```

## 7. Run the suite

Schema changes break history and feedback tests first.

```bash
docker compose run --rm api sh -c "ruff check . && python -m pytest -q"
```

## Project-specific rules

- **New table holding user data?** Ownership must be part of the `WHERE` clause in every query, and it needs an isolation test proving one user cannot read another's rows. See `tests/test_history.py`.
- **New column holding user content?** It must be masked before write — reuse `extract.mask` via `history.sanitize`, never write a second definition of what a masked phone number looks like.
- **Cascades:** child rows must not outlive their parent scan. `ondelete="CASCADE"` on the FK *and* `cascade="all, delete-orphan"` on the relationship, with a test.
- Guest scans are never persisted (R3). A migration adding a table that could hold guest data is a design error, not a schema task.
- Postgres is on host port **5433**; inside compose it is 5432.

## If autogenerate produces an empty migration

The models match the database. Either the change was already applied, or `db.py` was not actually edited — check `git diff api/app/db.py` before assuming Alembic is wrong.
